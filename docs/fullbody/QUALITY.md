# 配信用アプリの品質基準と実装前の検討

この文書は開発時の判断基準。実装済みの仕様は [README.md](README.md)、現在の処理方式は [TRACKING_DESIGN.md](TRACKING_DESIGN.md)、作業開始時のルールは [AGENTS.md](../../AGENTS.md) に置く。ここに挙げる検証がすべて自動化済み・合格済みという意味ではない。

## 目的

演者が普通に話す・笑う・うなずく・手を振る間、アバターが配信に使える自然さで追従すること。単一の指標を最適化せず、次を一緒に守る。

| 品質 | 配信上の意味 | 実装前に考えること |
| --- | --- | --- |
| 配信事故の防止 | 意図しない実映像・設定UIを出さない | 起動、設定終了、停止、障害、出力別窓で何が映るか |
| 応答性 | 顔・頭・口・手が演者から遅れすぎない | 撮影から描画まで、どの段が何を待つか |
| 滑らかさ | 話している間に頭や腕が停止と加速を繰り返さない | 検出間隔が長い・不均一でも何を描画するか |
| 姿勢の自然さ | 手首だけでなく肩・肘・掌・指が整合する | 途中の軌道、親子回転、骨長、遮蔽時の推定 |
| 意図との一致 | 反対の手が上がらず、口・瞬き・表情が対応する | 左右確認、鏡写し、複数表情の混合、確信がない入力 |
| 安定性 | 配信中の負荷変動や一時ロストで破綻しない | OBS併用、停止・再開、再検出、長時間使用、資源解放 |

カメラ1台では見えない肘や奥行きの正解を一意に得られない。分からない入力には、急な誤動作を避ける一貫した補完・保持・復帰が必要。

## 実装前に残す短い検討メモ

挙動変更の前に、以下を埋める。軽微な変更ではコメントや作業中の説明で足りる。大きな方式変更では設計文書へ残す。

```text
配信上の目的／再現条件:
現在のデータ経路と原因箇所（確認済み／仮説）:
変更前の比較対象と分かっている制約:
採用する変更・その理由:
検討した代案と採用しない理由（方式変更時）:
悪化し得る点と守る既存動作:
低fps・欠落・停止・再検出・負荷増加時の振る舞い:
何を測り、どんな結果なら今回の案を不採用にするか:
必要な検証／この環境で確認できないこと:
```

「自然にする」「平滑化を一段にする」「Workerへ移す」は手段であり、品質の合格条件ではない。入力の到着間隔と描画時の動きを予測してから方式を選ぶ。

## 今回の顔のカクつきから残す判断

2026-09-29、顔の遅延を減らした変更（画面の更新番号 `2026.09.28.2`）に対して、利用者から顔の動きが再びカクつくとの報告があった。これは未解決の回帰として扱う。

コードから確認できること:

- Face/Pose/Handを同じWorkerで順番に実行する。顔を先に通知しても、次の顔の撮影は全結果を返すまで開始しない。
- 頭は `headTarget` へ描画時に追従し、顔のなめらかさの既定値は80ms。体にある検出間隔に応じた応答時間の補正は使わない。
- 新しいテストは主に、一定目標への応答と顔の先行通知を確認していた。低fpsで連続して動く顔の見た目を、遅延と同時には評価できていなかった。

検証すべき仮説: 例えば4fpsでは観測間隔は250msになる。到着した目標へ速く追従するだけでは、次の観測まで動きがほぼ止まり、加減速が目立つ可能性がある。今回の利用者の実機でこれが主因かは未測定。推論時間の変動・描画の詰まり・データの欠落も切り分ける。

次の修正では、まず顔の観測間隔と描画された頭の角速度を比較する。候補は、推論スケジュールの見直し、観測間の補間、入力頻度に応じた追従など。どの方式も、負荷・追加遅延・停止時の漂い・他部位への影響を検討してから選ぶ。ここでは方式を固定しない。

比較対象の `3d3dc87` は腕の改善をpushした時点であり、顔の遅延が指摘されている。「全面的に良好な版」とは扱わない。現在の作業ツリーもカクつきが報告されており、テスト通過だけで改善済みとは扱わない。

## 観測・時間・処理負荷の設計

変更前に、対象データについて以下を追う。

1. 撮影時刻、顔・体・手それぞれの推論区間、送受信、姿勢計算、平滑化、描画、OBSでの表示。
2. 各段が参照する時計と座標系、保持する履歴、所有する平滑化、結果の期限。
3. 初回検出、確認中、追跡中、一時欠落、長い欠落、再検出、左右訂正、停止・再開での状態遷移。
4. 推論が処理能力を超えた場合の挙動。古い入力を蓄積しないこと、顔を優先した場合に体・手が止まらないこと。

顔の先行通知と顔の検出fps向上は別の変更。Workerを増やす案では、並列化の利点だけでなくGPU競合、メモリ、電力、OBSとの負荷競合を調べる。体と手の対応付けには、同じフレームを使うか、異なる時刻なら許容するずれと補正方法を決める。

平滑化を変更する前に、検出器内の処理、観測ノイズ除去、目標の補間、骨格への適用までを列挙する。状態や責任が重なっている箇所を減らす一方、必要だったノイズ除去や低fpsへの対処まで削除しない。

## 比較で測るもの

| 指標 | 測り方と注意 |
| --- | --- |
| 結果の到着間隔 | 顔・体・手別に中央値・p95・長い空白・欠落数。平均fpsだけにしない |
| 観測から描画までの遅れ | 同じ入力の時刻付き目標と描画姿勢を比較。推論時間、フィルタ遅延、通知待ちを区別する |
| 動作中の滑らかさ | 入力が動いている区間で位置・角度と速度の時間変化、停止と再加速、1描画フレームの急変を見る |
| 静止・停止の品質 | 静止時の揺れ、動作停止後の収束時間、行き過ぎ・漂い・巻き戻り |
| 姿勢と左右 | 実際のVRMのボーンと描画で、骨長、手首目標、肘の軌道、逆腕の誤反応、手首のねじれを確認 |
| 描画と継続負荷 | 描画間隔のp95・停止、WorkerとGPUの負荷、メモリの増え方。OBS併用時も区別して記録 |

80msなどの設定値は、そのまま実際のカメラ→画面の遅延ではない。ブラウザ内の計測をOBSを含む実測と混同しない。

絶対的な許容値は、基準環境・使用VRM・入力条件とセットで決める。未測定の数値を合格基準として捏造しない。初期段階では同じ入力の変更前後を比較し、改善対象と守る指標を変更前に決める。トレードオフが出たら数値・映像・制約を示す。

## 最低限の再現シナリオ

動作に関係する変更では該当する行を選ぶ。顔だけの変更でも、顔・体・手を同時に動かして部位間の干渉を確認する。

| 対象 | 入力シナリオ | 特に見るもの |
| --- | --- | --- |
| 頭 | ゆっくり連続した左右回転・傾き・うなずき、方向反転、急停止 | 遅れと観測間のカクつき、首と頭の二段階追従 |
| 顔 | 会話、五母音、笑顔、驚き、怒り、瞬きと視線移動の同時発生 | 口の追従、視線の中央戻り、意図しない表情、形状の跳ね |
| 腕 | 手を下から顔の横へ上げて静止、下ろす、胸の前で交差 | 途中の肘・肩、胴体への入り込み、左右の混同 |
| 手 | 掌→手の甲、握る→開く、片手ずつ映る、両手 | 手首のねじれ、回転途中の制限、指、逆腕の誤反応 |
| 遮蔽 | 肘だけ画面外、肩・顔・手の一時欠落、閾値付近を往復 | solverやIDの切り替えによる跳ね、保持、再検出の二重腕 |
| 配信操作 | 起動、設定開閉、プレビュー確認と取消、固定と解除、停止・再開 | 実映像の非表示、操作UI、保存設定、出力の一貫性 |
| 継続使用 | OBS併用、負荷の増減、カメラ切断、モデル変更、長時間利用 | カクつき、蓄積する遅れ、資源リーク、復帰 |

頭・腕の時間応答を変える場合は、検出4/7/10/15/24fps、描画30/60fps、結果の不規則な到着・一時欠落を対象にする。必要なら144fpsも追加する。すべての組み合わせを無条件に毎回実行するのではなく、低・中・通常頻度と境界条件を押さえ、変更範囲に応じて選ぶ。

テスト入力は静止目標だけでなく、連続動作→静止→逆方向の動作を含める。実装と同じ数式を期待値にしたテストだけにしない。実際のrawボーンと正面・側面の時間付き映像を比較する。

## 検証の範囲と不足の扱い

| 検証 | 現在の入口 | 分かること／分からないこと |
| --- | --- | --- |
| 単体・数値回帰 | `npm test` | 座標、左右、時刻、骨格、制御された入力での挙動。実カメラの自然さは保証しない |
| 画面全体 | `npm run test:browser` | 読み込み、配信UI、プレビュー、表情・手、出力。追跡入力の多くは制御したデータ |
| 起動と保存 | `npm run test:startup` | 起動時のカメラ・保存済みモデルなどの経路 |
| MediaPipe実モデル | `npm run test:tracking` | 公式写真・合成映像の推論、結果形式、停止・再開、CPUフォールバック。実際の会話動作とは別 |
| 腕の描画 | `npm run test:motion` | サンプルVRMの上げ動作と正面・側面の静止フレーム。頭や長時間配信は対象外 |
| 実機・OBS | 自動化された入口は未整備 | 利用環境・独自VRM・実際の会話・配信負荷・映り込みの確認が必要 |

今後優先して補うものは、時刻付きの連続入力を同条件で再生する仕組み、顔・頭の低fpsでの連続動作の回帰評価、実描画の動画比較、OBS併用時の計測。既存の通過件数でこれらの不足を埋めたことにしない。

利用者の映像やランドマークを記録する検証は、データ・保存先・用途を説明した上で依頼の範囲を守る。自動記録・外部送信を追加しない。まず合成入力と使用条件の明らかな既存fixtureを使う。

変更後は、変更理由、変更前後で確認した品質、使った入力・モデル・設定、未確認事項と回帰の有無を短く報告する。利用者から自然さの後退が報告された場合、数値テストが通っていても完了判定を見直す。

## 方式検討に使う一次資料

- [MediaPipe Face Landmarker / Web](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js): `detectForVideo`の同期実行とWorkerの利用。スレッドを分けることと観測頻度・最終表示の品質は区別して評価する。
- [1€ Filterの著者ページ](https://gery.casiez.net/1euro/): ノイズ除去と追従遅延の折り合い。フィルタ名の採用を品質の証明にしない。
- IK、VRM、スナップショット補間等の参照は [TRACKING_DESIGN.md](TRACKING_DESIGN.md#参照と判断) にまとめる。参考実装を採用する前に、入力、座標系、撮影頻度、遮蔽条件がこのアプリに合うか検討する。
